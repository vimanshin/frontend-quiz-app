## Как писать код в ответах

- Код полностью рабочий: без заглушек и плейсхолдеров.
- Выбирай самое простое читаемое решение. Readability важнее краткости.
- Практики актуальны на текущую дату. Для API, зависящих от версии (Vite, TypeScript, ESLint, Stylelint, Sass), при сомнениях сверяйся с официальной документацией через доступный Context7, а при его отсутствии — по официальной документации через веб-поиск.
- Используй современный синтаксис: `const`/`let`, arrow functions там, где они понятнее, template literals.
- Давай переменным и функциям осмысленные имена. Не используй однобуквенные имена, кроме счётчиков `i` и `j`.
- Не применяй сложную конструкцию без объяснения, зачем она нужна.
- Все пояснения и комментарии в коде пиши по-русски.
- Экспортируемым функциям задавай явные типы параметров и возвращаемого значения. Локальным переменным тип обычно не нужен — вывод типов справится.
- Не используй `any` и non-null assertion `!`. Если тип неизвестен — `unknown` с последующей проверкой; если элемент может отсутствовать — честная проверка на `null`.
- Перед каждой TypeScript-функцией добавляй комментарий этого вида:

```ts
// Функция: что делает функция и зачем она нужна
// Принимает: какие данные получает
// Возвращает: какой результат возвращает
```

Комментарий описывает смысл, типы описывают форму. Не дублируй в комментарии то, что уже сказано типом.

- Не комментируй очевидные присваивания. Добавляй inline-комментарии только в действительно сложных местах.
- Если я не просил «только код», после каждого фрагмента кода кратко объясняй:
  1. Что именно делает код — 2–3 предложения.
  2. Почему выбран этот подход.
  3. На что обратить внимание и что здесь новое.
- Если решений несколько, показывай самое простое и кратко упоминай альтернативы.
- Указывай на баги, антипаттерны и типичные ошибки новичков в моём коде, даже если я не спрашивал, и объясняй правильный вариант. Отмечай то, что действительно важно, а не каждую стилистическую мелочь.

### TypeScript в этом проекте

- **Vite не проверяет типы** — он их срезает при сборке. Проверку делает `tsc --noEmit`, встроенный в `npm run build`. Поэтому зелёная сборка без `typecheck` ничего не доказывает.
- Режим строгий: `strict`, `noUncheckedIndexedAccess`, `noUnusedLocals`, `noUnusedParameters`.
- `verbatimModuleSyntax` требует писать `import type` для импорта только типов.
- `erasableSyntaxOnly` запрещает `enum`, `namespace` и параметры-свойства конструктора: в проекте живёт только тот TypeScript, который исчезает при сборке без следа. Наборы констант оформляй через `as const`.
- Типы Node (`@types/node`) нужны только `vite.config.ts`, но видны и в `src/`. В браузерном коде не используй `process`, `Buffer`, `require` и модули `node:*`: `tsc` промолчит, а в браузере будет `ReferenceError`. Вместо `process.env` — `import.meta.env`.
- `any` и non-null assertion `!` не используются. Правильная реакция на «элемент может быть `null`» — проверка и early return, а не заглушение компилятора.
- Эти два запрета проверяет **ESLint**, а не компилятор: для `tsc` явный `any` и `!` совершенно легальны. Конфиг — `eslint.config.js`, в нём включены только те правила, которые уже описаны словами в инструкциях. Разделение простое: `tsc` отвечает за типы, ESLint за качество кода, Prettier за форматирование.

Подробные правила HTML, SCSS и TypeScript находятся в соответствующих субагентах (`.codex/agents/*.toml`). Не загружай все их инструкции в основной контекст без необходимости.
